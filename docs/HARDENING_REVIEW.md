# Evidence 模块补强审查 · v0.2 · 2026-10-02

## 当前判断

v0.1 可以跑通模块原型，但不足以据此声称已周全。v0.2 修复了下列可复现缺口，可进入队友接口联调。真实 Agent 行为、政策解释和比赛合规仍分别待验证；测试通过不等于裁决正确。

## 已修复的问题

| 问题及复现 | 影响 | v0.2 处理 |
|---|---|---|
| Judge 的 uncertainties=123 在运行校验中通过，JSON Schema 中失败 | 队友/前端对同一输出得到不同判断 | 运行时直接执行已公布 Schema；可选字段和扩展 JSON 都检查 |
| 数据不变、规范化代码改变，旧引用仅凭 source_sha256 仍能通过 | 相同编号可能指向不同解释/映射 | snapshot_id 同时绑定数据、规范化版本、映射和来源；增加过期拒绝及未绑定提示 |
| raw、pack、audit 分开读取 | 文件更新时可能拼出不一致材料 | prepare_case 一次读取生成快照；网页与下载使用同一份快照 |
| 实际浏览器下载把数字 5.0 重编码为 5，重算哈希不一致 | 下载文件无法按相同算法直接复现来源标识 | 完整快照保留服务端序列化文本，不在浏览器重编码原始数据 |
| 在合成行程之前加入远处 GPS 点，路线被算成约 85.4 km | 行程外位置造成虚假的绕路长度 | 只选记录的行程窗口内样本；保留排除索引和原文 |
| 司机 08:43 等待，但预约上车是 08:45 | 忽略提前等待是否可计费 | 增加预约时间到取消的 360 秒计算与政策解释提示 |
| rider_profile=null 导致 AttributeError | 不完整导入使调用异常退出 | 错误结构变为明确 InputError；真正缺失的可选数据保留缺失提示 |
| 重复 JSON 键、1e400、空/重复版本参数 | 静默覆盖或绕过输入语义检查 | 统一严格解析；明确大小、深度、有限数及查询参数边界 |
| 路线算出距离即可能让人误以为责任已明确 | 距离与政策判断被混淆 | 明确改道理由/费用依据仍须审查，Judge 忽略源数据复核标志时警示 |
| 上下车地点和行程标识缺少独立可引证条目 | 下游只能额外搜索 raw | 追加可引用的 trip_context，保留旧样例已有编号 |
| 原始文件被编辑后仍标成同一官方样例 | 来源版本不可追溯 | catalog 固定语义哈希；显式记录新版来源；禁止把 synthetic 重标为官方 |

技术依据：[Python JSON 文档](https://docs.python.org/3/library/json.html)提供 object_pairs_hook 与数值解析控制；本项目用它们拒绝重复键和非有限数。[JSON Schema 对象规范](https://json-schema.org/understanding-json-schema/reference/object)用于区分必填字段、可选字段类型和允许的扩展字段。这些边界是本项目的实现选择，不是主办方新增要求。

## 保持的团队接口

case_id、evidence_id、evidence_refs、policy_refs、decision 不改名。Evidence Pack 的 facts/policy 结构保持不变；snapshot_id、normalizer_version 和审计状态放在旁路快照中，不成为原核心对象的新必填字段。

decision 取值集合、refund_amount 单位、confidence 含义及人工复核门槛未擅自决定。字段校验不判断论据是否支持结论；模型可以引用真实编号却仍作出错误推理。

## 需要琪琪与团队提供或确认

按以下优先级推进即可，不需要一次准备齐所有材料：

1. **最先需要：队友当前代码仓库或 Rider/Driver/Judge 的真实输出 JSON。** 用于实际接口联调，确认 counterpoints、轮次记录、错误回退和前端定位行为。没有这些材料时，只能验证文档约定，不能声称已对接团队代码。
2. **团队业务约定：** decision 允许值；退款金额用“元”还是“分”、币种在哪个字段；confidence 是否只是模型自评；哪些情况转人工。还须确认“一轮陈述＋一轮回应”的双方执行顺序。建议由 Judge/编排负责人集中确认。
3. **主办方政策与新增数据：** 等待从到达、App 计时还是预约时间开始，提前到达是否计入；如有 Route Deviation 官方数据/政策，提供原文件或链接。在此之前保留现有歧义及 synthetic 标注。
4. **比赛工具与开发证明：** 确定真实使用 CodeBuddy 或 WorkBuddy 的开发步骤，并留存手册要求的真实截图/录屏。本轮由 Codex 辅助完成，不能转换成其他产品的使用证明。
5. **后续共享与模型环境：** 如要邀请队友，提供需要访问的 GitHub 用户名和预期权限；如要模型联调，确认框架、服务商和本地配置方式。不要把 API key 发到聊天或提交到仓库，真实乘客数据另行确认脱敏及授权范围。

## 仍然存在的能力边界

- 只有一个官方案例和一个 synthetic 案例；新增测试是在测试中构造的边界变体，不是新增官方评测样本，也没有 Judge 正确率。
- 未运行真实 Rider/Driver/Judge 模型。未验证提示词注入抵御、双方公平性、多轮回应质量和引用语义是否充分。
- 对真实道路、GPS 精度、交通拥堵、通话真实性、乘客通知是否被阅读没有独立验证。
- 对任意政策自然语言不做自动解释；对陌生字段只提示并保留原文，不能保证任何未来官方格式都无需适配。
- snapshot_id 检测版本不一致，但不提供历史快照数据库；保存的完整快照含原始字段，不是脱敏分享包。
- 本地只读服务不处理付款、退款或生产账号权限；不应直接开放互联网端口。

实际执行结果以 `VALIDATION.md` 及相应提交的 GitHub Actions 为准。
